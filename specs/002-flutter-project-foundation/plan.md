# Implementation Plan: Flutter Project Foundation

> **Feature number:** 002
> **Spec:** [`spec.md`](spec.md)
> **Author:** Codex
> **Date:** 2026-06-03

## Approach summary

Create the Flutter application scaffold at the repository root with Android and iOS targets only, then replace the default counter sample with a minimal app shell that already reflects the intended project boundaries: `core`, `data`, `domain`, and `presentation`. The implementation will add the approved package set, centralize runtime configuration behind a small `AppConfig` entry point backed by `--dart-define`, wire a single placeholder screen through Riverpod and GoRouter, and update platform manifests/plists for the required recording-related permissions. This satisfies the spec by producing a launchable baseline app, explicit top-level structure, build-time configuration access, dependency readiness, and a zero-warning analysis baseline without introducing feature logic that belongs to later stories.

## Architecture decisions

| Decision | Choice | Rationale |
| --- | --- | --- |
| Flutter app location | Generate the Flutter app at the repository root | The repository is already dedicated to the Flutter rewrite, so a root-level app keeps tooling, specs, and future CI straightforward and avoids an unnecessary nested project. |
| Platform scope | Generate only Android and iOS targets | The approved spec only requires mobile targets, so omitting web/desktop keeps the scaffold smaller and reduces unused generated files. |
| Android/iOS identity | Use `com.wrait.app` package/bundle base and align platform minimums with the Android reference | Reusing the established app identity and minimum supported versions minimizes divergence from the existing product baseline. |
| State management foundation | `flutter_riverpod` with a root `ProviderScope` | Riverpod gives a lightweight, testable dependency graph without forcing feature interfaces into this foundation story. It is simpler to seed now than introducing BLoC scaffolding before any feature state exists. |
| Navigation foundation | `go_router` with a single `/` route | This satisfies the dependency and app-shell readiness goals while respecting the clarified scope that only one placeholder screen is required in US-001. |
| Runtime configuration | `--dart-define` values surfaced through a typed `AppConfig` class | This avoids runtime file loading, keeps secrets out of committed source, and matches the spec requirement that build-specific values can be supplied without code edits. |
| Configuration validation | Parse and validate config once during app bootstrap with safe defaults and explicit failures for invalid required shapes | Central validation prevents configuration drift and gives developers immediate feedback during startup and tests. |
| Future database dependency | Add `sqflite_sqlcipher` now, but do not build storage abstractions yet | This satisfies dependency-readiness for the planned encrypted database path while keeping actual persistence design in scope for US-003. |
| Recording package selection | Add `record` rather than `flutter_sound` | `record` is the simpler cross-platform recording dependency for the planned file-based recording flow and requires less early setup for this foundation-only story. |
| Static analysis baseline | Use `flutter_lints` | It is the lowest-friction lint baseline for a new Flutter scaffold and should make the zero-warning requirement easier to satisfy without introducing team-specific lint churn this early. |
| Directory preservation | Create only minimal files needed to make each top-level layer concrete | This keeps `data` and `domain` visible in source control without inventing placeholder services or domain contracts before their stories arrive. |

## API contract details

No HTTP endpoints are implemented in US-001.

Implementation detail for this story is limited to the internal runtime configuration contract:

- `BACKEND_URL`
  Expected type: absolute URL string
  Behavior: defaults to the existing Android reference URL when not provided
- `PROXY_SECRET`
  Expected type: string
  Behavior: defaults to empty string so later stories can decide whether missing secrets should block specific backend calls
- `RECORDING_HARD_CAP_MS`
  Expected type: positive integer
  Behavior: defaults to `120000`; invalid values should fail validation in a developer-visible way during bootstrap or tests

The placeholder screen may render sanitized config values for verification, but it must not display secrets directly.

## Test strategy

Validation will focus on bootstrap correctness, configuration parsing, and static project health rather than feature behavior. Automated tests will cover configuration logic and basic app rendering, while manual verification will confirm platform launch and manifest/plist setup on Android and iOS targets.

### Automated tests

| Test case | Type | File |
| --- | --- | --- |
| `AppConfig` uses default values when optional defines are omitted | Unit | `test/core/config/app_config_test.dart` |
| `AppConfig` rejects non-positive hard-cap values | Unit | `test/core/config/app_config_test.dart` |
| `AppConfig` exposes explicit override values correctly | Unit | `test/core/config/app_config_test.dart` |
| Root app renders the single placeholder screen successfully | Widget | `test/app_smoke_test.dart` |
| `flutter analyze` completes with zero warnings | Static analysis | N/A command evidence recorded in `tasks.md` |

### Manual verification

1. Run `flutter pub get` and confirm dependency resolution succeeds without version conflicts.
2. Run `flutter analyze` and verify zero warnings.
3. Run `flutter test` and verify bootstrap/config tests pass.
4. Launch the Android app with `flutter run -d <android-device> --dart-define=BACKEND_URL=... --dart-define=PROXY_SECRET=... --dart-define=RECORDING_HARD_CAP_MS=120000` and confirm the placeholder screen appears.
5. Launch the iOS app with the same defines on an iOS simulator and confirm the placeholder screen appears.
6. Inspect the generated Android manifest and iOS Info.plist to confirm microphone and speech-recognition declarations are present.

## Integration notes

- The Flutter app will inherit environment defaults and platform minimums from the Android reference where applicable:
  - `BACKEND_URL` default: `https://wrait-backend.vercel.app`
  - `RECORDING_HARD_CAP_MS` default: `120000`
  - Android `minSdk`: `26`
- `PROXY_SECRET` will be accepted as configuration input but will not yet be used by network code in US-001.
- The chosen package set is intentionally forward-looking for US-002 through US-006, but no repository, service, or API client implementations will be introduced in this story.
- No downstream API or data consumers are affected because this work only creates the new client foundation.

## Rollout & migration

This is initial-project scaffolding, so rollout is simply merging the new Flutter foundation into the repository and using it as the base for subsequent stories.

- No feature flags are needed.
- No backward-compatibility migration is required inside the Flutter codebase because it does not yet exist.
- The existing `wrait-android` reference remains untouched and serves only as an implementation reference during the rewrite.

## Risks & mitigations

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| One or more approved plugins introduce Android or iOS dependency conflicts in a fresh scaffold | Medium | High | Add dependencies incrementally, run `flutter pub get` early, and prefer the minimal approved package variants selected in this plan |
| iOS minimum deployment target or Android min SDK remains at Flutter defaults instead of product requirements | Medium | High | Explicitly patch generated platform files and verify values during manual launch validation |
| Runtime config defaults drift from the Android reference | Low | Medium | Centralize defaults in `AppConfig` and validate them with unit tests |
| The directory structure becomes cluttered with premature abstractions | Medium | Medium | Keep only bootstrap files plus placeholder-preserving files for empty layers; defer repositories/services/models to later stories |
| Secrets are accidentally surfaced in UI or logs while proving config access | Low | High | Never render `PROXY_SECRET` verbatim and avoid logging raw configuration values |
| Standard generated Flutter files overshadow existing planning docs or repo conventions | Low | Medium | Generate in place once, then review the scaffold and keep project docs under their existing top-level directories |
