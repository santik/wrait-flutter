## Overview

The Flutter app no longer relies on an iOS plugin that requires CocoaPods, and
Flutter now detects that the active iOS plugin set is available through Swift
Package Manager. However, the iOS project still contains leftover CocoaPods
integration, including a Podfile, Pod-generated xcconfig includes, Pod-linked
framework references, and Pod-specific build phases. That stale wiring produces
tooling noise, adds unnecessary maintenance burden, and keeps the iOS project
in a partially migrated state.

This feature removes obsolete CocoaPods integration from the iOS client project
while preserving the ability to build and run the app on supported iOS
simulators and devices. The result should be a clean Swift-Package-Manager-only
iOS setup for the current dependency set, without changing app behavior or
introducing unrelated feature work.

> **Reminder:** This spec must be **purely functional and technology-agnostic**.
> Describe the problem and requirements, not the solution. Technology choices
> belong in `plan.md`.

## User stories

- As a developer, I want the iOS project to stop carrying unused CocoaPods
  integration so that the native setup matches the current dependency set.
- As a developer, I want Flutter iOS tooling to stop warning about leftover
  CocoaPods integration when no active plugin needs it so that build output is
  easier to trust.
- As a developer, I want iOS simulator and device builds to continue working
  after the cleanup so that project maintenance improves without breaking the
  app.

## Acceptance criteria

- [x] The iOS project no longer depends on CocoaPods artifacts to build the app
      for the current Flutter dependency set.
- [x] Pod-specific project references, Pod-specific build phases, and
      Pod-specific config includes that are no longer needed for the active iOS
      plugin set are removed from the iOS project.
- [x] Flutter iOS commands no longer report that all plugins are Swift Packages
      while CocoaPods integration still remains in the project.
- [x] The app still launches successfully on at least one supported iOS
      simulator after the cleanup.
- [x] Existing non-iOS development flows remain unaffected by the cleanup.
- [x] This story does not change app behavior, persistence behavior, or user
      experience beyond native-project/tooling cleanup.

## Non-functional requirements

- **Performance:** iOS build and launch time should not regress because of the
  cleanup and may improve by removing obsolete native wiring.
- **Security:** The cleanup must not weaken current secure-storage,
  authentication, permission, or encrypted-database capabilities.
- **Reliability:** iOS build configuration should remain internally consistent
  after removing Pod references, and the app must continue launching on a
  supported simulator.
- **Scalability:** The native project should better match Flutter’s current SPM
  path so future dependency maintenance is simpler.
- **Observability:** Validation evidence must show that the CocoaPods warning is
  gone and that an iOS launch still succeeds afterward.
- **Maintainability:** Native project files should no longer contain obsolete
  Pod-specific references for dependencies that now resolve through Swift
  Package Manager.

## Out of scope

- Changing the active Flutter plugin set unless required to complete the
  CocoaPods removal safely
- Reworking Android, macOS, web, or backend configuration
- Introducing new product features or UI changes
- General iOS project redesign unrelated to removing obsolete CocoaPods wiring
